# CrowdShield — ML Predictor: Early Warning Model

Predicts, from a zone's recent trend (not just a snapshot), the
probability it crosses a danger threshold in the near future.

## READ THIS FIRST — the honest limitation

This is trained **only on Module F1's own social-force simulation**,
run hundreds of times with varied venues/turnout/triggers. It is
**not** trained on real historical stampede data — no usable public
dataset of that kind exists (real stampedes are rare, chaotic, and
nobody was logging density/flow sensors during them, including Karur).

**Say this plainly in the pitch:** the model predicts patterns that led
to escalation in our own physics simulation, not an empirically
validated real-world outcome. This is the same honest limitation every
system in this space has — being upfront about it is more credible
than pretending otherwise.

## What's real here

- **861 real training examples**, generated by actually running Module
  F1's simulation 300 times across all 5 real venue maps, varied scale,
  varied turnout (300-30,000), and randomized trigger events
- **Genuine early/late window split**: features come ONLY from the
  first 30% of each simulation's timeline; the label is whether the
  LATTER 70% crossed a danger threshold. This is what makes "predicts
  before it happens" real rather than a snapshot classifier.
- **Honestly evaluated on a held-out test set** (not training data):
  93.1% accuracy, 96.5% precision, 91.0% recall — see the full
  confusion matrix and classification report printed by
  `train_model.py`
- **Feature importances are reported, not hidden**: `early_density_max`
  and `early_panic_slope` dominate; `is_chokepoint`/`is_vip_corridor`
  show ~zero importance. This makes sense on reflection — chokepoints
  naturally produce higher measured density anyway, so once the model
  sees actual density readings, the static label adds no new
  information beyond what's already reflected there.

## Setup

```bash
pip install -r requirements.txt --break-system-packages
```

## Generate training data (already done once — `training_data.csv` is included)

```bash
python generate_training_data.py --n-runs 150 --output training_data.csv --seed 42
```

Takes ~1.3s per run. Writes incrementally, so a long run left interrupted still has partial usable data.

## Train the model (already done once — `model.joblib` is included)

```bash
python train_model.py --data training_data.csv --output model.joblib
```

Prints full honest evaluation metrics — re-run this yourself to see the same numbers.

## The live-vs-training feature gap (important, real, documented)

The model was trained on F1's simulated **continuous per-agent panic
fraction** — a concept that only exists in the simulation (thousands
of individual simulated agents each have a stress value). Live Module D
readings don't have that — real/live sensors report discrete signals
(push-wave detected: yes/no; thermal collapse: yes/no), not a
continuous panic measurement.

**The fix used here:** the live dashboard substitutes a proxy —
whether *any* physical signal (push-wave OR thermal collapse) fired for
that reading, then computes the same mean/slope math over that 0/1
proxy that the model expects for "panic." This is a reasonable,
explainable adaptation, but it is not identical to the training
feature's exact definition. State this plainly if asked in Q&A: it's
an honest engineering trade-off between what the simulation could
measure and what live sensors can actually report.

## Files

- `feature_extraction.py` — turns F1 frames into early/late window
  features + label (tested against real simulation runs)
- `generate_training_data.py` — runs many varied F1 simulations,
  builds the dataset
- `train_model.py` — trains + honestly evaluates the classifier
- `main.py` — FastAPI service, `/predict-danger` endpoint
- `training_data.csv` — the actual generated dataset (861 rows)
- `model.joblib` — the actual trained model
